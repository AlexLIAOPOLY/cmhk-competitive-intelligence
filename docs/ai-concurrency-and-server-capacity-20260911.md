# AI 并发调度与 50 人服务器容量准备

日期：2026-09-11。用户目标：周报、竞对分析、小竞 AI 等可以同时使用，第一阶段按约 50 人同时发起 AI 请求准备。

## 2026-09-13 三 Key 独立限额与智能分流

- 全局三把 Key 现按各自的分钟窗口和并发槽单独记账，调度器在真正发请求前原子选择“当前进行中最少、本分钟已用最少”的 Key，避免多人或多任务集中冲击第一把。
- 每把默认保守14次/分钟、3个同时请求；三把的全应用默认容量自动为42次/分钟，全局同时请求仍受8个上限及前台/后台保留位约束。显式设置 `REQUESTS_PER_MINUTE` 时仍以运维指定的全局值为准。
- 429/`rate_limit`、额度不足、鉴权失败或模型权限不足会只冷却出问题的 Key，当前请求立即改选其余 Key；普通网络中断在同一 Key 上有界重试，避免把网络问题误认为额度问题。
- 调度文件只保存 Key 的脱敏哈希标识、分钟计数、占用数和冷却原因，不保存密钥明文。
- 真实网关验收：通过新调度器连续发起3次当前正式模型请求，落点依次为 Key 1/2/3；三次均 HTTP 200、`finish_reason=stop`、完整返回 `OK`，隔离计数回读为1/1/1。

## 本次确认与修复

原 Web 已使用多线程，并不存在一把锁串行锁住所有 AI。但全局每分钟 14 次调用、后台共用同一总计数、缺少用户公平排队，会让批量写作与互动分析相互影响；配置还有最多 15 次的隐藏上限。新闻洞察另有整项功能互斥锁，后到用户会直接被拒绝。本次移除这一功能总锁，保留按相同输入防重复的持久检查点；相同新闻输入等已有结果，不重复推理。

新增 `ai_dispatch.py`，所有已盘点的常规推理入口统一接入：

- `open_llm_request` 负责 urllib 首次调用、切换 Key、重试、非流式读完，以及流式/音频响应关闭前的容量占用。
- LangChain 同步、异步、普通与流式共用同一调度；关闭 SDK 内层重试，防止一次预约中暗中发多次请求。异步排队可取消，取消不留下将来会消耗额度的后台等待线程。
- 周报写作/审核、业绩摘要、竞对数据与新闻洞察、四库 AI、RAG、图片/语音、TTS、监控诊断与战略新闻均覆盖。业务层不再先预约一次后又由底层重复预约。
- 文件锁只保护短暂记账，模型生成期间不持有文件锁。全局并发、前后台容量、按用户/工作流排队均有上限；不同用户轮流服务。同一用户的积压不能填满整个队列。
- Web 使用已认证用户 ID 的哈希作为公平队列身份；聊天后台线程继承上下文。原有角色授权继续生效，不自动给未授权账号开放模块。
- 失败、取消、完整读完、显式关闭和进程退出会释放占位。容量不足返回可重试状态；竞对洞察显示排队，不误报已经告警。浏览器放弃即时洞察后停止排队/流式请求；已有聊天的断线续接与报告后台任务仍遵循各自生命周期。
- `/api/ai-capacity` 提供需登录授权的容量读数，不包含密钥、用户 ID、提示词或回答。HTTP 连接积压队列从标准默认值扩大为 128，以接收突发连接。

## 默认参数与边界

下面变量均以 `CMHK_INTERNAL_AI_` 开头。配置要在 Web、后台进程和调度器中保持一致。

| 变量后缀 | 默认值 | 含义 |
|---|---:|---|
| KEY_REQUESTS_PER_MINUTE | 14 | 每把 Key 的保守分钟请求上限 |
| KEY_MAX_CONCURRENT | 3 | 每把 Key 的同时请求上限 |
| REQUESTS_PER_MINUTE | Key 数 × 14 | 全应用每分钟上限；显式配置时覆盖自动合计值 |
| MAX_CONCURRENT | 8 | 同时占用的模型请求总数 |
| INTERACTIVE_CONCURRENT_RESERVE | 2 | 后台不能占用的前台名额 |
| BACKGROUND_CONCURRENT_RESERVE | 1 | 前台不能占用的后台名额 |
| PER_USER_CONCURRENT | 2 | 单个互动用户同时占用上限 |
| PER_WORKFLOW_CONCURRENT | 3 | 单个后台工作流同时占用上限 |
| INTERACTIVE_RESERVE | 4 | 每分钟为互动请求保留次数 |
| BACKGROUND_RESERVE | 2 | 每分钟为后台保留次数 |
| MAX_QUEUED | 200 | 全局等待队列长度 |
| PER_USER_QUEUED | 4 | 单个互动用户等待上限 |
| PER_WORKFLOW_QUEUED | 24 | 单个后台工作流等待上限 |
| INTERACTIVE_QUEUE_TIMEOUT | 180 | 互动请求排队时限（秒）；调用方预算更短时取较短值 |
| BACKGROUND_QUEUE_TIMEOUT | 900 | 后台排队时限（秒）；调用方预算更短时取较短值 |
| RATE_STATE_PATH | 系统临时目录内统一文件 | 同一实例全部进程必须使用相同本地路径 |

这是单主机、同一 PID 命名空间的多进程实现。不同容器或多台服务器不能各自用一份本地文件来假装共享容量。旧版本进程与新版本不应长期混跑，须通过标准队列统一加载常驻服务。

当前三 Key 的应用侧默认为 42 次/分钟，但不意味着 50 人能在同一秒生成；全局同时请求仍限制为8，且会为前台与后台互留容量。超过当前分钟或并发槽会排队，超过调用方时限则明确返回可重试状态。

## 验证结果

- 50 个不同用户同时从真实 `/api/competitor-insight-stream` HTTP 路由请求，混合 6 次实际周报写作函数和 4 次 LangChain 聊天，使用本地确定性模拟模型：60/60 完成、实际峰值 8 路；前台和报告确实重叠；结束时 active=0、queued=0、发起计数恰好 60。最终一轮耗时 9.155 秒，互动请求 P50 4.901 秒、P95 7.773 秒。
- 上述模拟模型固定延迟 0.4 秒、报告延迟 1.2 秒，并在隔离状态中设置 6000 RPM 以测应用调度。该延迟和成功率不能解释为真实模型容量或真实业务报告生成速度；未生成或发送正式报告。
- 真实网关少量并发探测：4/4 HTTP 200、`finish_reason=stop`、完整 `OK`，观察到 2 路同时在执行。前台约 1.2 秒完成，后台等待本分钟容量后约 32.6–32.8 秒完成。此证据只支持小规模当前可用，不代表 50 路真实模型压测通过，也不代表三把 Key 的预算互相独立。
- 最后一轮相关回归 270 项通过、4 项已确认的旧断言明确排除，另 4 个子测试通过；此前扩展功能专项 223 项通过。覆盖用户公平、队列上限、前后台互相保留、流式关闭、取消、进程退出、跨进程容量、SDK 重试计数、同输入复用和已有模型恢复流程。
- 普通 Playwright 验证实际页面与选项交互，1440×1000、390×844 均显示“AI 请求较多 · 5 秒后自动重试，请稍候”，控制台无 error/warn。浏览器使用隔离接口响应；Browser 插件未提供，按技能采用已有 Playwright。截图在 `/tmp/cmhk-ai-ui-20260911/`。
- 扩大执行 `tests/test_web_app_curation.py`：184 项通过，4 项既有断言失败：CSS/JS 固定旧版本号两项、AWS 数据固定截至 2025 年/40 点两项（实际已经有 2026 年/42 点）。本次未把这些断言改成通过，也未报告全仓库测试全绿。

## 上服务器的验收顺序

1. 先向网关管理员核实模型的 RPM、TPM、最大并发、预算及多 Key 是否共享池；本次没有擅自提高正式额度。根据真实请求 token 分布和耗时申请容量，再改变参数。
2. 正式多人部署应迁移到生产 Web 服务入口，把长报告、审核和语音放到持久任务队列，前台通过任务 ID 查询进度、取消与恢复。当前 `http.server` 不能仅换一台机器就视为生产架构；Python 官方明确不建议将其直接用于生产：[官方说明](https://docs.python.org/3.12/library/http.server.html)。这一步尚未实施。
3. 多容器/多机时，将限流、并发租约和公平队列放到共享协调服务（例如 Redis 原子脚本）；用户会话、任务、结果与缓存也须放到共享持久存储，不能只迁移限流文件。Redis 官方提供原子限流模式：[INCR 与 Lua](https://redis.io/docs/latest/commands/incr/)。这一步尚未部署和验收。
4. 在测试环境按 5→10→20→50 用户逐级施压，混合一份完整周报、竞对分析、聊天和 TTS。测首次状态时间、队列等待 P50/P95、首 token/完成耗时、429/5xx、内存/CPU、任务完成率，并做取消、网关限流、掉线、进程重启与重复提交故障注入。要求后台任务不挤死前台、恢复不重复写库/发送。
5. 最后再对真实模型执行受控的 50 用户混合负载，明确验收等待时限和费用预算；通过后才能宣布服务器支持目标容量。本次没有将模拟压测或 4 次探测替代这项验收。
