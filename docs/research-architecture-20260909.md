# 研究流程架构优化 · 2026-09-09

用户在第一轮保留架构的优化之后，明确允许适当调整架构，重点缩短运行时间。

## 实施后的流程

六组研究 → **3路公司终审队列** → 单协调器汇总 → 单写入步骤更新四库 → 原有洞察及发布。

初始研究仍覆盖41家公司、473项指标。最终审核从一个串行执行器改成最多3个独立、长期复用的 harness；公司之间并行，公司内部逐指标校验、保存。未配置任何额外模型额度，共用原有跨进程限流和前台交互预留。公司、主体、期间、币种、原文校验、失败语义及写库门禁保留。

此次改变执行队列与存储方式，没有合并不同公司的模型上下文，也没有把长JSON批量输出或减少审核步骤当作提速手段。

## 真实瓶颈与改动

2026-09-09六组研究03:00:14启动，最后一组05:26:05完成，约2小时26分；最终审核05:26开始，10:53的记录仍未完成。期间存在重启/中断，不能把整个时间跨度都算成连续模型耗时。

旧终审检查点为224,030,018字节。每次指标保存都会将全部公司的原文和报告重新序列化、写入，恢复与页面轮询也读取这一大文件。

新存储拆分为：

- `final-review.json`：公司级索引、运行编号、并发数、总体状态。
- `final-review-companies/<公司SHA-256>/progress.json`：该公司当前进度和原文元数据，绑定运行编号。
- 同目录 `pages.json`：完整原文，仅初次保存/联网补查后更新。

指标保存不重写全文。根索引更新由短锁串行保护；各公司进度由独立执行器原子写入。最终候选事实、审核事实及原六组汇总文件只由协调器按原顺序写入。`final-review.lock` 防止两个进程重复执行同轮终审。

旧检查点在开始恢复时无损迁移。新格式按公司与运行编号检查作用域；即使根索引丢失，也不能把另一轮的公司进度混入当前轮。进程在单项保存后退出，恢复只继续剩余指标；根索引落后时从公司文件恢复较新的进度。

前端回读兼容两种格式，返回相同的公司、指标与来源字段，新格式只读取终审进度及原文元数据。已完成的旧历史任务不强制迁移。恢复旧代码前需要先导出完整旧式终审检查点，不能直接让旧版本读取新索引。

## 验证

- 真实旧归档中的35个公司报告迁移后，报告及全部原文逐项相等。根索引从约224MB变为4,211字节；本次样本的单项进度保存约100KB，全文文件修改时间保持不变。原文没有删除或截断。
- 等量队列基准：6家公司、12个固定80ms模型步骤，预热依赖、每种配置两次，实际执行检查点与汇总写盘。串行中位数1.1354秒，3路并行0.3932秒，减少65.4%；全部候选事实内容一致。这是受控执行基准，不是整轮线上耗时承诺。
- 真实内部模型3家公司小批量：3个独立模型实例，5次逻辑调用，65.311秒结束；2项审核通过、1项失败。失败项在每公司最多2次调用的隔离验证预算内未通过，保持失败，没有放宽门禁。真实调用包含网关限流/密钥轮换因素，不能推算整轮提速比例。
- 自动化覆盖并发上限、上下文隔离、串行/并行候选事实相等、唯一汇总写入、逐项恢复、原文不重复写入、旧格式迁移、索引写入失败恢复、运行编号与计划隔离、跨进程锁。子进程在首项落盘后直接退出，重启只执行第二项且不重新搜索。
- 研究、可靠性、前端数据交付及四库回归共168项通过。新格式回读实测返回3个审核报告，原文正文不进入前端响应，结果维持2通过/1失败。

## 效果边界

最大的预期收益来自终审的并行吞吐和消除大文件重复写盘。模型轮次及指标数量没有削减；实际耗时仍受来源响应、模型服务、全局限流和失败重试影响。本次未额外运行完整473项付费研究，下一轮才能获得同范围整轮实测。当前证据证明队列并行、持久化与恢复能力及原有门禁，不能宣称所有公司数据已齐或耗时固定减少三分之二。
