# CMHK主项目实时错误监控

## 当前运行边界

- 监控对象只包括 CMHK 竞争情报主项目。
- `Token Hub` 及 `com.liaowang.cmhk-token-hub-crawl` 明确排除。
- 生产 LaunchAgent 已设置 `CMHK_ALERT_NOTIFICATIONS=1`；只有开启后首次发现的真实错误才可进入 LLM 分析与群通知链路。
- 群消息策略固定为：**只发错误**。正常、心跳、日报和“系统正常”均不发送；恢复不另发新消息，只在证据与结案 LLM 都通过后更新原告警卡片。
- 每条错误在发送前必须完成一轮真实内部 AI 分析；重要等级、确认事实、推断、故障原因、故障影响、重要程度说明、建议解决方案及是否需要人工介入均需通过契约。故障时间由监控证据锁定，不交给模型生成。AI 分析失败或字段不完整时无限期留在待重试队列，禁止用规则文本冒充 LLM。
- 发送身份固定为机器人 `Alex的狂热粉丝`，App ID/Profile 均锁定为 `cli_a9575e70ae799cb2`，禁止退回用户身份。
- 告警卡片、LLM 诊断、错误证据和错误台账统一转换为简体中文；飞书用户身份仍通过真实 `open_id` 校验。
- 服务重启后以 LaunchAgent 当前 PID 的真实启动时间为新一代边界：重启前的日志型错误只在本地标记为已解决，不再做 AI 分析或群告警。首次观察某个日志从文件末尾建立水位，不回放历史错误。任务归档中仍失败、卡死或待恢复的真实任务不受此规则影响。

## 严重程度

- `P1 紧急`：常驻服务停止、调度心跳停止、定时扫描漏跑、主爬虫/Feishu 关键阶段失败或任务卡死。
- `P2 高`：四库刷新、AI 审核、报告生成等任务最终失败，旧数据通常仍保留。
- `P3 中`：部分来源或质量门禁失败、TTS 等非核心产物失败；仍需处理，但不代表主系统整体停止。

严重程度先由确定性规则给出最低等级，再由 AI 根据任务、错误、影响和证据给出最终重要等级及说明。AI 可以提高等级，但不得降低规则给出的最低等级，也不得臆测未提供的内部事实。故障时间、恢复类型、恢复时间、验证证据和实际动作均由程序锁定，LLM 只能据此归纳，不能改写。

每条实际错误告警固定包括：任务名称、LLM 重要等级、LLM 核对的故障时间、LLM 故障原因、LLM 故障影响、原始错误证据、LLM 重要程度说明、LLM 建议解决方案、是否需要人工介入、告警 ID 和实际 AI 模型。

结案分为 `自动修复后恢复`、`服务重启后恢复`、`已确认任务正常`、`故障条件已清除`、`误报` 和 `新口径接管`。只有系统确实记录了修复动作，才允许使用“自动修复”；仅仅没有再次命中条件时先进入“恢复待验证”。拿到正向证据后，再由真实 LLM 输出结案总结、恢复原因、验证结论和剩余风险，之后才可更新群卡片。后台与群卡片读取同一份诊断和结案对象。

媒体指标任务对飞书明确返回的HTTP 429／`rate_limit`在进程内最多尝试5次，采用1／2／4／8秒封顶的指数退避和随机抖动；只有重试耗尽才写入错误日志。每个群发送时段只有在目标群、正文和图片均完成消息回读后，才写入`sent_slots`和`slot_deliveries`。媒体指标日志告警也只凭对应时段的这份正向账本结案，不能仅因后续日志安静而判定恢复。

## 告警样式

告警使用飞书 Card 2.0 的克制型单列结构：标题只突出重要等级、任务、故障时间和处理状态；主体依次显示 LLM 故障影响、故障原因、重要程度判断和建议解决方案；原始错误证据默认折叠。P1/P2/P3 分别使用低饱和红、橙、蓝作状态提示，不使用大面积装饰、拥挤表格或无意义图标。

卡片末尾使用受信任的飞书 `open_id` 生成真实超链接 `@廖望Alex`，不能由错误日志或 LLM 文本注入。所有动态文本在渲染前先脱敏、转换为简体中文并转义飞书 Markdown 标签。

样式依据飞书官方的[消息内容结构](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/im-v1/message/create_json)与[消息创建接口](https://open.feishu.cn/document/server-docs/im-v1/message/create?lang=zh-CN)，信息字段参考 [Google SRE 事件管理指南](https://sre.google/resources/practices-and-processes/incident-management-guide/)的清晰分级、角色和处置结构；未照搬消费级通知模板。

## 错误台账与处理闭环

错误自动写入原工作簿的新子表 `项目错误告警`，子表 ID 为 `j1AY6G`。每个告警 ID 只保留一行，系统自动维护 A:L 与 O:Q；人工字段 M `处理人员` 和 N `处理状态` 在创建后不会被监控同步覆盖。

卡片只提供一个 `已处理` 按钮。点击后，独立监听器会依次校验应用身份、目标群、原消息 ID、告警 ID 和点击者 `open_id`，再把点击者的简体中文飞书姓名写入 M 列、把 N 列写为 `已处理`，最后将对应卡片按钮置灰。新故障只发故障处理群；旧群里的历史卡片仍可点击处理。并发点击采用先到先得，后续点击不能覆盖首位处理人；重复事件按事件 ID 幂等处理。

告警发送前必须先完成对应台账行的在线写入与回读，避免卡片先到、台账行后到造成按钮回写失败。台账增量追加先写数据，再按飞书返回的实际行范围补样式；读取使用明确的 `A1:Q<工作表行数>` 单元格范围，不受中间空白行影响。历史重复告警 ID 优先选择已有处理人的行，否则使用最早行，不再令整个按钮回调链停止。

按钮监听器：

```text
com.liaowang.cmhk-project-monitor-card-actions
```

监听器只消费 `card.action.trigger`，不具备发送群消息的路径。飞书开发者后台必须先为应用 `cli_a9575e70ae799cb2` 启用“卡片回传交互”，监听器出现 ready 证据后才可加载到生产环境。

## 发送安全链

错误只有同时满足以下条件才可能发送：

1. 监控进程启动时明确带有 `CMHK_ALERT_NOTIFICATIONS=1`；默认值和缺失值都视为关闭。
2. 错误是在总闸开启后首次发现；影子期历史错误不会在启用时补发。
3. 错误首次发现时间不早于目标群的 `notify_from_hkt`；切换目标群时不会补发尚未关闭的历史故障。
4. 内部 AI 返回通过完整字段、等级下限、时间一致性和布尔类型校验的一轮分析。
5. `lark-cli whoami --as bot --profile cli_a9575e70ae799cb2` 实时返回预期 App ID。
6. 报障路由目标的实时群名、模式、状态和内外部属性与白名单完全一致。
7. 每个实际发送群使用独立幂等键。
8. 发送后以 bot 身份回读消息，核对群 ID 和实际 sender App ID。

发送目标群：

- `战略竞对故障处理群`

`揭榜-竞争对手与行业情报监测AI应用` 与 `竞对AI项目需求沟通群` 仍保留在 `targets` 白名单中，供历史卡片回调校验，但均为 `alert_notify=false`，不再接收新的报障卡片。战略快讯和全量新闻通报仍沿用各自独立的总群路由，不受本报障路由调整影响。可用 `CMHK_ALERT_TARGET_ROLES` 临时覆盖路由。

发送成功但回读暂时失败时，会保留 `message_id` 并只重试回读，绝不因回读失败重复发送。

## Web 提交与运行加载解耦

代码提交和双远端同步不等待战略新闻任务。需要加载 Web 代码时执行：

```bash
./scripts/queue_web_app_reload.sh
```

命令只写入一个可合并请求并立即返回；单例后台工作器会把期间所有修改合并为一次最新源码同步。它优先等待战略新闻连续两次空闲后加载，最长只等到香港时间次日凌晨 00:00；若届时旧任务仍未结束，允许在明确的每日截止点中断旧 Web 进程并加载排队版本。运行目录同步和重载都由后台工作器完成，调用任务无需保持终端或延迟 Git 提交。
